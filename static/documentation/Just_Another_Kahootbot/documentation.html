Developer Documentation

This guide is for contributors working on the repository (not for deployment). Follow the branching and merge workflow below: create feature branches, merge them into dev, and then once dev is tested and approved it will be merged into master by maintainers.

Note: If you want to deploy or run the bot, see the installation guide.

Project Components (quick)

  • KahootBot — core bot logic: WebSocket connection, question parsing, answering.
  • Swarm — manager for running and supervising multiple KahootBot instances.

Branching: Create a Feature Branch

Always create a descriptive feature branch. Work and push there; pull requests should target dev. 


# Start from the latest dev
git checkout dev
git pull origin dev

# Create your feature branch
git checkout -b feature/your-descriptive-name

Use names like feature/add-logging or fix/reconnect-timeout.

Committing & Pushing

Keep commits logical and focused. Commit messages should explain what and why. 


# Stage changes
git add .

# Commit with a clear message
git commit -m "feat: add exponential backoff to websocket reconnects"

# Push the branch to remote
git push origin feature/your-descriptive-name

Prepare to Merge into dev

Before creating a pull request to dev, make sure your branch rebases cleanly on top of the latest dev. This reduces merge conflicts and keeps history easier to reason about. 


# Update local dev
git checkout dev
git pull origin dev

# Rebase your branch onto dev
git checkout feature/your-descriptive-name
git rebase dev

# If conflicts occur, fix them, then:
git add 
git rebase --continue

If rebase becomes messy, you can also merge dev into your branch: 


# Alternative: merge dev into your branch (preserves merge commits)
git checkout feature/your-descriptive-name
git merge dev

# Resolve any conflicts, then commit the merge
git push origin feature/your-descriptive-name

When and How to Squash Commits

Important: do not squash every time. Squash only when you need to tidy up the branch history — e.g. when you have multiple WIP/fixup commits that should be combined into a single logical change, or when maintainers request a single commit for a patch. Preserve meaningful, separate commits if they reflect distinct steps or rationale.

Recommended ways to clean up commits:


# Interactive rebase to squash the last N commits (example: last 5)
git checkout feature/your-descriptive-name
git rebase -i HEAD~5

# In the interactive editor: mark commits to squash (s / fixup) as needed,
# save and close the editor to complete the rebase.

You can also use --autosquash with properly formatted fixup commits: 


# Mark a commit as fixup when creating the commit
git commit --fixup 

# Then run interactive rebase with autosquash
git rebase -i --autosquash dev

After rewriting history (rebasing/squashing), push safely with: 


# Force push safely (preferred)
git push --force-with-lease origin feature/your-descriptive-name

Do not force-push to branches shared by multiple collaborators without coordination.

Create a Pull Request to dev

Open a pull request targeting dev. Add a clear description, testing steps, and link related issues. Address review comments and keep the PR focused on a single change if possible. 


# Example workflow summary:
# 1. Ensure branch is up-to-date with dev (rebase or merge)
# 2. Optionally tidy commits (interactive rebase) if necessary
# 3. Push (force-with-lease if history changed)
# 4. Open PR against dev

What Happens Next

Once PRs to dev are reviewed and approved, maintainers will merge dev into master at appropriate release times. This centralizes integration and testing on dev.
